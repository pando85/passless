# Session-scoped browser isolation

## Status

Accepted design for issue #433.

## Problem

Agent profiles currently combine two concepts that need different lifetimes:

- a profile defines static authority (credential namespace, RP policy, registration policy, browser configuration), while
- an agent/harness execution is ephemeral and needs its own browser state.

The runtime currently permits one managed principal session and one active browser bookkeeping slot per profile. That makes a profile behave like a runtime singleton and prevents several harness sessions from using the same authority while keeping independent cookies, storage, login state, and Chromium processes.

A fixed CDP port also makes concurrent Chromium processes impossible because only one process can bind that port.

## Decision

### Profiles define authority; principal sessions define runtime isolation

`ProfileId` remains the identity of configured authority. `PrincipalSessionId` is the authoritative identity of one launched principal runtime. It is generated by Passless and is not derived from a harness-provided name.

A profile may have more than one live principal session when configured to allow it.

### Browser leases are session-owned

A principal-created browser lease is owned by exactly one `PrincipalSessionId`.

Browser reuse is allowed only when the requesting principal session is the recorded owner of the same live lease. The following are never sufficient reasons to reuse a browser:

- matching `ProfileId`;
- matching UID/GID;
- matching CDP endpoint or port;
- matching external harness/session label;
- matching policy configuration.

When the owning principal session terminates, expires, or is revoked, its browser lease is revoked, its Chromium process is terminated, and its per-lease browser profile is cleaned up. Other sessions under the same profile are unaffected.

The browser process manager already creates a distinct runtime directory and Chromium `--user-data-dir` for each `BrowserLeaseId`; this design makes the higher-level ownership model match that existing isolation boundary.

### Concurrency is explicitly bounded

Profiles gain:

```toml
max_concurrent_sessions = 4
```

The default is `1` for backward-compatible resource limits. Values greater than one allow independent principal sessions to run concurrently under the same authority profile.

Browser isolation itself is not optional: even when the limit is one, a new principal session never adopts a browser created by a previous principal session.

When `browser_cdp_expose = "port"` and `max_concurrent_sessions > 1`, `browser_cdp_port` must be `0` (or omitted) so every Chromium process receives an ephemeral loopback port.

Example:

```toml
[agents.profiles.coding]
mode = "same-user"
principal_user = "agent"
max_concurrent_sessions = 4
browser_cdp_expose = "port"
browser_cdp_port = 0
```

### `same-user` and `isolated` keep their credential semantics

Browser-session isolation is independent of authenticator identity:

- `same-user` sessions may share the same human credential/RP authority while their browsers remain separate;
- `isolated` continues to mean a profile-owned credential/authenticator identity.

Users should not create generated profiles or switch to `isolated` merely to obtain separate browser cookies/storage.

### Harness session discovery

The preferred integration is one harness/MCP process per logical harness session:

```text
harness session A -> MCP process A -> principal session A -> browser lease A
harness session B -> MCP process B -> principal session B -> browser lease B
```

Passless then needs no OpenCode-, Codex-, or other harness-specific session identifier. The principal capability and `PrincipalSessionId` form the security/runtime identity.

If a harness multiplexes several logical conversations through one MCP process and one stdio connection, Passless cannot infer those hidden conversation boundaries. Such a harness must either spawn MCP per session or transmit an explicit per-call session identifier to a router. External session identifiers may be added later as correlation metadata, but they must not become authority-bearing identifiers or implicitly resume old browser state.

## Runtime model

The managed-session registry is profile-indexed but stores a collection of sessions instead of a singleton:

```text
ProfileRuntime(coding)
  sessions:
    PrincipalSession A
    PrincipalSession B
    PrincipalSession C

  active browsers:
    A -> BrowserLease A
    B -> BrowserLease B
    C -> BrowserLease C
```

Principal IPC authentication selects the managed session by its unforgeable launcher capability proof and then validates peer credentials, namespaces, cgroup, and process ancestry against that exact session.

## Required invariants

1. At most `max_concurrent_sessions` live principals exist for a profile.
2. A principal session owns at most one active browser lease.
3. `EnsureBrowser(session)` reuses only that session's live lease.
4. `EnsureBrowser(session B)` never adopts a lease belonging to session A or an admin-launched browser.
5. Session teardown cleans only resources owned by that session.
6. Profile disable, policy-wide invalidation, credential revocation, and daemon shutdown may deliberately clean every session/browser for the affected profile.
7. A fixed CDP port is rejected when profile concurrency is greater than one.
8. Browser ports are transport details, never browser identities.

## Lifecycle

```text
launch principal
  -> generate PrincipalSessionId
  -> register managed session
  -> (on demand) EnsureBrowser
       -> allocate new BrowserLeaseId
       -> create lease-<id>/profile
       -> launch Chromium on an ephemeral loopback CDP port
       -> record PrincipalSessionId -> BrowserLeaseId

principal exits / expires / is revoked
  -> cancel session-owned pending work
  -> revoke sign context for its browser lease
  -> revoke/terminate browser lease
  -> clean lease runtime/profile directory
  -> remove managed session
```

## Non-goals

This change does not make direct loopback CDP a hostile-process security boundary. Port mode remains intended for trusted local agents. A stronger boundary would require process/network isolation or an authenticated CDP proxy/pipe design.

This change also does not implement resumable browser sessions. Reusing an external logical session string must not recover old cookies or browser authority. A future resume feature would require a Passless-issued resume capability and an explicit persistence policy.

## Validation

The implementation is complete when tests cover at least:

- two principal sessions under one profile when the configured limit permits it;
- enforcement of the concurrency limit;
- independent browser leases for sessions A and B;
- repeated `EnsureBrowser` within session A reusing only A's lease;
- termination/revocation of A cleaning A's browser while B remains live;
- principal IPC capability selection among multiple sessions under one profile;
- fixed CDP port rejection for concurrent profiles;
- profile disable/shutdown cleaning all remaining sessions and leases.
