# ADR 0003: Portable TPM-resident credential keys

- **Status:** Accepted
- **Date:** 2026-07-23
- **Decision owners:** Passless maintainers
- **Implementation status:** Core implemented (PR #354, pending merge); seed-provisioning UX change and one-time ES256 migration accepted, pending implementation; remaining hardening tracked under [Remaining work](#remaining-work)
- **Implements:** [issue #314](https://github.com/pando85/passless/issues/314)
- **Depends on:** [soft-fido2 v0.15.0](https://github.com/pando85/soft-fido2/pull/126) (credential key-provider abstraction in the high-level `Authenticator`)
- **Related documentation:** [TPM_PORTABLE.md](../TPM_PORTABLE.md), [TEE_HARDWARE_COMPATIBILITY.md](../TEE_HARDWARE_COMPATIBILITY.md)
- **Background:** [discussion #312](https://github.com/pando85/passless/discussions/312), proof of concept [`mimi89999/webauthn_tpm_portable`](https://github.com/mimi89999/webauthn_tpm_portable)

## Context

The current TPM backend generates WebAuthn credential keys in software, serializes the complete
`soft_fido2::Credential`, encrypts it with AES-GCM, and seals the AES key to a device-local TPM
primary key. This protects credentials at rest, but the WebAuthn private key is returned to host
memory whenever a credential is unsealed and is cached as part of the runtime credential.

Issue #314 proposes replacing this sealed-software-key model with a portable TPM-resident
signing-key model: a deterministic storage parent is imported into each enrolled TPM from a single
high-entropy recovery seed, and each WebAuthn signing key is generated by `TPM2_Create` under that
parent. The synchronized credential record carries the TPM-produced `TPM2B_PUBLIC` and
`TPM2B_PRIVATE` blobs plus protected metadata. Any TPM containing the same portable parent can load
the blobs and sign, while the credential signing private key never exists in host memory.

This is supported by the TPM 2.0 object model. The TCG TPM 2.0 Library Part 3 specification states
for `TPM2_Import`:

> If the new parent is not fixedTPM, then that object will be loadable on any TPM (including SW
> versions) on which the new parent exists.

This is not only a new storage adapter. It requires changing the credential cryptography boundary
in `soft-fido2`, because key generation, self-attestation signing, and assertion signing previously
operated directly on raw 32-byte private-key bytes inside `soft-fido2-ctap`.

## Decision summary

Passless adopts the portable TPM-resident signing-key model for the `tpm` backend, behind an
explicit opt-in (`--tpm-portable` / `PASSLESS_TPM_PORTABLE`). The first implementation:

- Generates new **ES256** WebAuthn signing keys inside the TPM; the private key never leaves the TPM.
- Derives a deterministic portable storage parent from a recovery seed and imports it via `TPM2_Import`.
- Allows a credential created on one provisioned TPM to be loaded and signed for by another TPM
  provisioned from the same seed.
- Keeps the existing UHID/CTAP architecture, discoverable credentials, credential management,
  `credProtect`, and PIN/UV behavior.
- Freezes a Passless-specific, versioned portable-parent format (not the proof-of-concept labels).
- Provides an explicit, non-destructive **migration** from the legacy sealed format to the portable
  format via a one-time ES256 import (`passless tpm migrate`) that preserves existing RP
  registrations, in addition to plain re-registration. See [Migration](#migration).
- Prefers the existing **constant zero signature counter** for portable credentials (a mutable
  global counter does not synchronize safely across offline devices).

The software-key provider remains the default in `soft-fido2`; existing software credentials remain
readable. The `local` and `pass` backends are unchanged.

## Implemented scope (PR #354)

### `soft-fido2` crypto-provider abstraction (v0.15.0)

A credential key-provider boundary was added to the high-level `Authenticator`, released as
`soft-fido2` v0.15.0 ([pando85/soft-fido2#126](https://github.com/pando85/soft-fido2/pull/126)):

- `Authenticator<C, K = SoftwareCredentialKeyProvider>` with `with_config_and_key_provider` and
  related constructors.
- `CredentialKeyProvider` trait: `generate(algorithm) -> (opaque key material, public key)` and
  `sign(algorithm, key_material, message) -> signature`.
- `makeCredential` key generation, self-attestation signing, and `getAssertion`/`getNextAssertion`
  signing all go through the provider; CTAP code no longer assumes `key_material.len() == 32`.
- `SoftwareCredentialKeyProvider` reproduces the existing ES256/EdDSA behavior and is the default.
- Provider identity and key-material format are versioned so a credential cannot be sent to the
  wrong provider.

### Portable parent (`cmd/passless/src/storage/tpm/portable/`)

- `parent.rs` — `PortableParent`: deterministic derivation of the parent ECC P-256 scalar, public
  point, and storage `seedValue` from the recovery seed; `TPM2_Import` wrapper; persistence at owner
  handle `0x81000001`; startup verification of the parent Name and full template; `remove`.
- `provider.rs` — `TpmCredentialKeyProvider` implementing `CredentialKeyProvider` for ES256
  (COSE alg `-7`): `TPM2_Create` under the portable parent, `TPM2_Sign`, DER-encoded ECDSA output,
  strict load-time template revalidation (required because the parent is not `fixedTPM`), and
  transient-handle flush on every path.
- `kdf.rs` — KDFa (SP800-108), KDFe (SP800-56A), AES-128-CFB, and HMAC helpers.

**Frozen format (version 1):**

| Field | Value |
|---|---|
| Provider ID | `tpm-portable-v1` |
| Format version | `1` |
| KDF | HKDF-SHA256 |
| KDF salt label | `passless.portable.v1` |
| KDF info labels | `parent-ecc-key`, `parent-seed-value` |
| Parent key type | ECC NIST P-256 storage key |
| Parent attributes | `restricted \| decrypt \| userWithAuth` |
| `fixedTPM` / `fixedParent` (parent) | clear / clear |
| Name algorithm | SHA-256 |
| Symmetric child protection | AES-128-CFB |
| Persistent handle | `0x81000001` (owner hierarchy) |
| Child key type | ECC NIST P-256, ECDSA-SHA256 |
| Child attributes | `sensitiveDataOrigin \| sign \| userWithAuth`, `fixedTPM`/`fixedParent` clear |

The `TPM2_Import` wrapper performs ECDH key agreement, KDFe to derive the wrapping key, KDFa for the
inner integrity, AES-128-CFB encryption of the sensitive area, and HMAC integrity — byte-compatible
with the proof-of-concept's on-the-wire structure but using Passless-specific derivation labels.

### Backend wiring

- `passless-core/src/config.rs`: `TpmBackendConfig.portable` and `BackendConfig::Tpm { portable }`,
  driven by `--tpm-portable` / `PASSLESS_TPM_PORTABLE`; `TpmAction` enum (`Provision`/`Status`/`Remove`).
- `cmd/passless/src/authenticator.rs`: `AuthenticatorService<S, P, K = SoftwareCredentialKeyProvider>`
  is now generic over the key provider, with `with_pin_storage_and_key_provider` /
  `with_shared_storage_and_key_provider`. Portable mode constructs the service with
  `TpmCredentialKeyProvider`.
- `cmd/passless/src/main.rs`: portable wiring in both the agent and non-agent startup arms.
- `cmd/passless/src/storage/tpm/mod.rs`: `TpmStorageAdapter::new_portable` seals the
  credential-metadata AES key under the **portable parent** (`fixedTPM`/`fixedParent` clear) so the
  metadata key is portable for the same reason as the signing blob; uses proper `tss-esapi`
  marshaling (no unsafe `TPM2B` casts). The legacy sealed path is byte-compatible and untouched.

### Provisioning CLI (`cmd/passless/src/commands/tpm.rs`)

`passless tpm provision | status | remove`:

- `provision --generate`: generate a random 32-byte seed and print it once.
- `provision --seed-fd <N>`: read the hex seed from a file descriptor. *(superseded — see below)*
- `provision` (no source): secure interactive prompt (`rpassword`, no echo).
- `status`: report provisioning state, format version, persistent handle, and parent Name.
- `remove --confirm`: evict the parent and delete provisioning metadata.

The seed is never accepted as a positional/normal argument; it is `Zeroizing` and zeroized after use.

### Tests (swtpm)

- `cmd/passless/tests/tpm_portable.rs`: provision, ES256 generate, sign, software-verify;
  **create-on-A / sign-on-B** with the same seed; wrong-seed rejected; tampered blob rejected.
- `cmd/passless/tests/tpm_portable_storage.rs`: metadata sealed on swtpm A unseals on swtpm B with
  the same seed; wrong seed fails.
- Both run in CI (two `swtpm` instances). `cargo clippy --all-features --all-targets -- --deny warnings`
  and `cargo fmt --check` are clean; x86_64 and aarch64 build/test jobs pass.

### Documentation

`docs/TPM_PORTABLE.md` (overview, provisioning, recovery-seed handling, threat model, migration,
signature-counter policy, interoperability matrix), plus README and `TEE_HARDWARE_COMPATIBILITY.md`
updates.

## Seed provisioning UX

### Context for the change

The first implementation accepted the recovery seed through `--seed-fd <N>` (a file descriptor).
This is the least intuitive of the safe transport options: users do not think in file-descriptor
numbers, and arranging one in a shell is awkward (`passless tpm provision --seed-fd 3 3< seed`).
Because the feature is not yet released, the interface can be changed without a compatibility
constraint.

### State of the art

| CLI | Mechanisms (safest → least safe) | Notes |
|---|---|---|
| **openssl** `-passin` | interactive prompt (default) · `file:PATH` · `fd:N` · `stdin` · `env:VAR` · `pass:STR` | Canonical one-flag/multiple-source model; `pass:` documented as insecure (visible in `ps`). |
| **Vault** | `vault login` prompt · `VAULT_TOKEN` env · token-helper file · `@file` / `-` (stdin) | Env used for *revocable* tokens, not long-lived secrets; `-` = stdin, `@path` = file. |
| **age / sops** | `-i keyfile` · passphrase prompt · `SOPS_AGE_KEY_FILE` / `SOPS_AGE_KEY` env | File-based identity is the headline; env secondary. |
| **gpg** | pinentry prompt (default) · `--passphrase-file` · `--passphrase-fd` · `--passphrase` (insecure) | Same prompt/file/fd/literal split as openssl. |
| **ssh-keygen** | interactive prompt (default) · `-N`/`-P` literal (insecure) | Prompt-first. |
| **1Password `op`** | `op signin` (biometric) · `OP_SERVICE_ACCOUNT_TOKEN` env · `op://…` secret references · `op read` | Reference a secret in a manager so it never touches argv/disk. |
| **gh** | `gh auth login` prompt · `--with-token` (stdin) · `GH_TOKEN` env | Stdin via an explicit flag. |

The recurring safe transports, ranked for a **long-lived, irrevocable** recovery seed:

1. **Interactive prompt** (no echo) — safest and most intuitive for humans.
2. **Generate in-tool** — the seed never enters from outside.
3. **File path** — intuitive ("put it in a file"); safe if the file is `0600`.
4. **Run-a-command / secret reference** — seed never touches disk or argv; integrates with secret managers.
5. **stdin** — pipe/CI friendly.
6. **fd** — niche; awkward in shells.
7. **env var** — risky for an irrevocable seed (`/proc/<pid>/environ`, inherited by children, crash dumps); Vault uses env only for revocable tokens.
8. **literal on argv** — never (visible in `ps`/history).

### Decision

Replace `--seed-fd <N>` with two intuitive, self-describing flags, keeping the existing safe sources:

| Source | Flag | Behavior |
|---|---|---|
| Interactive prompt | *(default, no flag)* | `rpassword`, no echo. Used when no source flag is given. |
| Generate | `--generate` | Generate a random 32-byte seed; print once with a backup warning. |
| File | `--seed-file <PATH>` | Read the first line of `PATH`, trim, decode hex. Warn if the file is group/other-readable (recommend `0600`). |
| stdin | `--seed-stdin` | Read stdin to a string, trim, decode hex. Enables `pass show fido2/seed \| passless tpm provision --seed-stdin`. |

Constraints:

- `--generate`, `--seed-file`, and `--seed-stdin` are **mutually exclusive** (clap `ArgGroup`).
- The seed is **never** accepted as a normal/positional argument or via environment variable.
- All seed buffers remain `Zeroizing` and are zeroized after use; the seed is never logged.
- The seed format is unchanged: exactly 32 bytes / 64 hex characters.
- `--seed-fd` is **removed** (the feature is unreleased; `--seed-stdin` and `--seed-file` cover its
  use cases more intuitively).

**Not adopted:** a `--seed-cmd <COMMAND>` source (secret-manager integration) and an environment
variable. Secret-manager users are served by piping into `--seed-stdin`
(e.g. `pass show … | passless tpm provision --seed-stdin` or `op read op://… | …`). An environment
variable is rejected because an irrevocable recovery seed in the environment is exposed through
`/proc/<pid>/environ`, inherited by child processes, and may appear in crash dumps.

### Rationale

`--seed-file` is the headline improvement: it matches the dominant convention (age `-i`, gpg
`--passphrase-file`, openssl `file:`, Vault `@file`) and is immediately discoverable in `--help`.
`--seed-stdin` covers scripting and secret-manager piping (gh `--with-token`, openssl `stdin`,
Vault `-`). Discrete self-describing flags were chosen over an openssl-style unified
`--seed <SOURCE>` argument because each flag is obvious without learning a `prefix:value` grammar,
which best serves the "human intuitive" goal. The interactive prompt remains the default and safest
path for a person provisioning by hand.

## Migration

Passless must offer an explicit way to move credentials from the **legacy sealed-software TPM
format** (software key sealed to a device-local primary) to the **portable TPM-resident format**,
without forcing users to re-register at every RP. This is issue #314's migration option A. It is a
committed part of this feature (implementation pending), not an optional follow-up.

### Approach: one-time ES256 import

A legacy ES256 credential is migrated by importing its existing private key into the TPM under the
portable parent, so the credential keeps the **same credential ID and public key** and the RP
registration remains valid. The signing key becomes TPM-resident from that point on.

Per credential:

1. Require a provisioned portable parent (`passless tpm provision`); refuse otherwise.
2. Load and unseal the legacy credential once (unseal the AES key from the device-local TPM,
   decrypt the record, reconstruct the credential with its raw private scalar).
3. Recompute the public key from the private scalar and confirm it matches the stored public key.
4. Import the private scalar as a TPM signing object under the portable parent via `TPM2_Import`
   (same ECDH/KDFe/KDFa/AES-128-CFB/HMAC wrapper used for the parent). The child template is ECC
   P-256 / ECDSA-SHA256 with `sign | userWithAuth`, `fixedTPM`/`fixedParent` clear, and
   **`sensitiveDataOrigin` clear** — because the private value is supplied, not TPM-generated. This
   is the key difference from newly created portable keys (which use `TPM2_Create` with
   `sensitiveDataOrigin` set).
5. `TPM2_Load` the imported blob and `TPM2_ReadPublic`; **verify the TPM public key exactly equals
   the original registered public key**. Abort without writing on any mismatch.
6. Run a local sign/verify self-test with the imported key against the known public key.
7. Build the new portable record carrying over credential ID, RP ID/name, user, algorithm,
   `credProtect`, `cred_random` (hmac-secret state), creation time, and discoverable flag; the
   signing blobs are the imported `TPM2B_PUBLIC`/`TPM2B_PRIVATE`; metadata is sealed under the
   portable parent (with the AAD binding from [Remaining work](#remaining-work) once implemented).
8. Back up the legacy record, then **atomically write** the new portable record.
9. Zeroize the legacy raw private key and all temporary buffers.
10. Only replace/remove the legacy record after the new record passes the local sign/verify test;
    keep the backup until then (rollback by restoring the backup).

### CLI

```text
passless tpm migrate [--credential-id <ID> | --all] [--dry-run] [--backup-dir <PATH>]
```

- `--dry-run`: report which legacy credentials are migratable (ES256) and which are not (EdDSA),
  changing nothing.
- `--all`: migrate every eligible legacy credential.
- `--credential-id <ID>`: migrate one credential.
- `--backup-dir <PATH>`: where legacy backups are kept (default: a `.backup` subdirectory).
- Idempotent: credentials already in portable format are skipped.

### Edge cases and caveats

- **EdDSA credentials cannot be migrated** (the TPM provider is ES256-only in v1). They are reported
  by `--dry-run`, left in the legacy format, and the user re-registers if they want portability.
- Both discoverable and non-discoverable (allow-list) credentials are migratable.
- `cred_random` is carried into the new sealed metadata so `hmac-secret` keeps working.
- Migrated credentials use the **constant zero signature counter** like other portable credentials;
  any legacy counter value is not carried forward (documented RP clone-detection implication).
- Migration **cannot retroactively guarantee** the key never existed outside hardware — the legacy
  key was software. This is documented; the non-exportability guarantee applies from migration
  onward.
- The legacy sealed format stays readable throughout; nothing is destroyed until the migrated
  record is verified.

## Remaining work

Tracked against issue #314. [Migration](#migration) is a committed part of this feature; its
implementation and the final legacy-format deprecation are pending. The remaining items are grouped
by priority.

### Required security and correctness (issue mandates)

- **Metadata binding (AAD).** Portable credential metadata is encrypted with AES-GCM using a sealed
  key but with **no** additional authenticated data (`cmd/passless/src/storage/tpm/mod.rs:347`). The
  issue requires the record to be cryptographically bound to its credential ID, RP ID, algorithm,
  provider version, and TPM public object. Add AAD over those fields so a sealed metadata blob
  cannot be transplanted between credentials.
- **Parent/child authorization decision.** The portable parent and child signing keys currently use
  **empty** `authValue` (`portable/parent.rs:506`, `portable/provider.rs:108`) and children have
  `fixedParent` clear (`provider.rs:313-314`) — the proof-of-concept defaults. The issue states
  empty auth "must not be adopted without an explicit decision." Decide and document: per-device
  local parent `authValue` (retaining the same Name/seed), independent child auth, whether
  `fixedParent` can be set on children, and interaction with Passless PIN/notification UV.
- **Parameter-encrypted sessions.** Portable-parent `TPM2_Import`/`Create` use a null-auth or
  password session (`parent.rs:216`, `provider.rs:107`), so the sensitive blob is **not** protected
  by parameter encryption (the legacy seal path does use an HMAC session). Add parameter-encrypted
  HMAC sessions for sensitive portable-parent command parameters.
- **Persistent-handle collision detection.** Provisioning calls `evict_control` without first
  checking whether `0x81000001` holds an unknown/different object (`parent.rs:224-240`). Detect
  collisions and refuse to evict an unknown object.
- **TPM-clear / replacement detection.** A missing parent or Name/template mismatch returns a
  generic `Error::Other` (`parent.rs:144-152`). Return an actionable error distinct from "credential
  corrupt."
- **Downgrade protection.** The format version is checked on *sign* but nothing stops an older
  Passless from overwriting a newer record on *write* (`provider.rs:287-289`). Reject unknown/newer
  record versions before writing.
- **Capability check.** There is no `TPM2_GetCapability` query for ECC P-256 / ECDSA-SHA256 /
  AES-128-CFB before registration (`provider.rs:249-251` is a hardcoded algorithm comparison).
  Detect unsupported TPM capability before registration with an actionable error.

### Portability completeness

- **`cred_random` / PIN portability.** `TpmPinStorage` seals PIN and `cred_random` state under a
  device-local primary (`fixedTPM`/`fixedParent` set, `pin_storage/tpm.rs:164-165`), not the portable
  parent, so hmac-secret state does not move with the credential. Decide whether to make PIN state
  portable or to document it as intentionally device-local.
- **Agent-mode wiring.** Agent profiles build `TpmStorageAdapter::new_with_options()` with
  `portable: false` (`agent/storage_factory.rs:289`, `agent/config.rs:266`). Wire portable storage
  into agent profiles (or explicitly scope it out).

### Migration and rollout (Phase 5)

- **Implement `passless tpm migrate`** as designed in [Migration](#migration): one-time ES256 import
  with `sensitiveDataOrigin` clear, public-key verification, local sign/verify self-test, `--dry-run`,
  backup, atomic write, rollback, and zeroization. Not yet implemented.
- **Mark the sealed format legacy** once the portable implementation and migration are stable.

### Testing

- **Mock external provider** test in `soft-fido2` proving CTAP paths never inspect opaque key material.
- **Concurrency** test (ESAPI context state under concurrent requests).
- **Transient-handle leak** test (repeated operations).
- **Power-loss / restart** during provisioning and write (must not destroy an unrelated persistent
  object or a valid credential).
- **Fuzzing** of the portable record parser and the TPM public/private blob decoder boundary.
- **Cleared-TPM / occupied-handle** actionable-error tests.
- **Hardware interoperability matrix** (Intel PTT, AMD fTPM, discrete TPMs). Currently
  swtpm↔swtpm only; the matrix in `TPM_PORTABLE.md` is a template, not yet exercised.

### Deferred by design (issue non-goals / staged)

- **EdDSA** from the TPM provider (ES256-first; EdDSA is a stated non-goal for the first implementation).
- Cloud synchronization service, macOS support, and cryptographic revocation of a provisioned device
  (explicit non-goals).

## Consequences

**Positive**

- Newly created WebAuthn signing keys never exist in host memory, closing the cold-boot/swap/core-dump
  and unseal-time exposure of the sealed-software model.
- Credentials are portable across TPMs provisioned from the same seed (validated swtpm↔swtpm).
- The `soft-fido2` provider boundary keeps software keys as the default and leaves `local`/`pass`
  users unaffected.
- Existing RP registrations can be preserved when moving off the legacy format through the one-time
  ES256 migration (`passless tpm migrate`).
- The seed-provisioning UX (`--seed-file`, `--seed-stdin`, prompt, `--generate`) is safe and intuitive.

**Negative / accepted risks**

- Recovery-seed compromise plus access to synchronized blobs allows cloning (documented threat model).
- No per-device cryptographic revocation; a removed device retaining the parent and old blobs can
  keep using those credentials.
- Constant zero signature counter for portable credentials (RPs may treat this as a cloned-authenticator
  signal; accepted and documented).
- Metadata binding, authorization hardening, and several robustness items are not yet implemented
  (see [Remaining work](#remaining-work)); the portable backend should be considered pre-1.0 until
  the "Required security and correctness" items land.
