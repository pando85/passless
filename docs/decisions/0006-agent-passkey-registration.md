# ADR 0006: Agent-Driven Passkey Registration via Daemon-Backed WebAuthn Extension

- **Status:** Accepted
- **Date:** 2026-08-03
- **Decision owners:** Passless maintainers
- **Implementation status:** Phases 1-5 implemented; protocol types, registration grants, daemon handler, extension override, and tests complete
- **Related decisions:** [ADR 0005](0005-delegated-autonomous-authentication-redesign.md), [ADR 0003](0003-portable-tpm-credential-keys.md)
- **Amends:** the daemon-backed extension path of ADR 0005
- **Supersedes:** the deferred registration decision in ADR 0005

## Context

ADR 0005 established a daemon-backed MV3 extension that overrides `navigator.credentials.get()` for headless, autonomous authentication. The extension intercepts authentication requests, forwards them to the daemon's `/sign` HTTP endpoint, and returns a duck-typed `PublicKeyCredential` to the relying party. The daemon enforces grant policy, RP allowlists, credential refs, audit, and signs via the `CredentialKeyProvider` abstraction — keeping the private key out of the browser.

However, that design only covers **authentication** (GetAssertion). Registration (MakeCredential) still requires human interaction: the browser calls `navigator.credentials.create()`, which either triggers the native security-key modal (UHID path) or falls through to the default browser behavior. An agent process cannot register a new passkey without a human present.

This matters for autonomous workflows where an agent needs to:
- Register a new passkey on a relying party during initial setup
- Rotate credentials without human intervention
- Provision credentials on new services as part of CI/CD pipelines

The registration flow is structurally different from authentication:
- **Authentication** operates on an *existing* credential (the grant references a known `CredentialRef`)
- **Registration** creates a *new* credential (no `CredentialRef` exists yet)

The existing grant system requires a non-empty `CredentialSet` at grant time, which is incompatible with registration where no credential exists yet.

## Decision

Extend the daemon-backed extension to also override `navigator.credentials.create()`, adding a `/register` HTTP endpoint to the daemon that handles MakeCredential operations. The design mirrors the authentication path: the extension intercepts the call, the daemon constructs the credential and keypair, and the extension returns a duck-typed `PublicKeyCredential` to the page.

### 1. Extension Override for `credentials.create()`

The MAIN-world content script (`main.js`) gains a `navigator.credentials.create()` override alongside the existing `get()` override. The override:
- Reads `window.location.origin` from the calling frame (same origin-safety model as `get()`)
- Serializes `PublicKeyCredentialCreationOptions` (rp, user, challenge, excludeCredentials, pubKeyCredParams)
- Forwards to the broker via `window.postMessage` on the same per-session channel
- The broker and worker follow the same validation and HTTP dispatch pattern as authentication
- The worker POSTs to `http://127.0.0.1:<port>/register` with the same bearer token

### 2. Daemon `/register` Endpoint

A new `RegisterHandler` in `cmd/passless/src/agent/register.rs` (mirroring `sign.rs`):

**Request:**
```rust
pub struct RegisterCredentialRequest {
    pub origin: String,
    pub rp_id: String,
    pub challenge_b64u: String,
    pub user_id_b64u: String,
    pub user_name: String,
    pub user_display_name: Option<String>,
    pub rp_name: Option<String>,
    pub exclude_credentials: Vec<String>,
    pub user_verification: bool,
    pub cross_origin: bool,
}
```

**Response:**
```rust
pub struct RegisterCredentialResponse {
    pub credential_id_b64u: String,
    pub authenticator_data_b64u: String,
    pub attestation_object_b64u: String,
    pub client_data_json_b64u: String,
}
```

**Validation pipeline (in order):**
1. Bearer token lookup (same as `/sign`)
2. Origin structural verification (reuse `verify_origin_structural`)
3. Operation lock acquisition
4. Registration grant resolution (see §3)
5. RP ID match against grant scope
6. Ceremony policy check: `profile_config.rule_for_rp(rp_id).register.authorization == Allow`
7. Exclude list check: none of the excluded credential IDs match existing credentials for this RP
8. Audit event: `Register` action recorded
9. Key generation via `CredentialKeyProvider::generate()`
10. Credential ID generation (random bytes)
11. `authenticatorData` construction with attested credential data (rpIdHash + flags + signCount + AAGUID + credIdLen + credId + COSE public key)
12. `clientDataJSON` construction with type `"webauthn.create"`
13. Attestation statement (self-attestation, format "none")
14. Storage write via `CredentialStorage::write()`
15. Return response

The private key is generated by the `CredentialKeyProvider` and never leaves the daemon. For software keys, the key material is stored in the credential. For TPM keys, the key is generated and sealed by the TPM, and only the sealed blob is stored.

### 3. Registration Grant Model

Registration grants differ from authentication grants because no credential exists yet. The design uses a **two-phase grant model**:

**Phase 1: Registration Grant**
- Scoped to RP IDs only (no credential refs required)
- Created via a new `RequestRegistration` IPC command:
  ```rust
  AdminRequest::RequestRegistration {
      profile_id: ProfileId,
      rp_id: String,
      max_session_ttl: u64,
      reason: Option<String>,
  }
  ```
- The policy engine evaluates `rule_for_rp(rp_id).register.authorization`
- Returns a `RegistrationGrantId` (distinct from `GrantId`)

**Phase 2: Post-Registration Authentication Grant**
- After successful registration, the daemon returns the new `CredentialRef` in the response
- The agent process can then request a standard authentication grant for the new credential
- Alternatively, the daemon can automatically create an authentication grant bound to the new credential (configurable per profile)

This maintains the invariant that authentication grants always reference existing credentials, while registration grants only need an RP ID.

### 4. Authenticator Data Construction

The daemon builds `authenticatorData` directly (same pattern as the sign handler), without routing through `soft_fido2::Authenticator`. This avoids the UHID round-trip and keeps the key in the daemon.

**Structure:**
```
rpIdHash (32 bytes) || flags (1 byte) || signCount (4 bytes) || attestedCredentialData
```

Where `attestedCredentialData` is:
```
AAGUID (16 bytes) || credentialIdLength (2 bytes) || credentialId (variable) || credentialPublicKey (COSE key)
```

The COSE public key is derived from the generated keypair. For ES256 (algorithm -7), this is the uncompressed P-256 point encoded as a COSE_Key.

### 5. Attestation Format

Self-attestation with format "none" — consistent with the current MakeCredential behavior. The attestation statement is empty (`{}`). This is sufficient for all target relying parties (Gitea/Forgejo) and avoids the complexity of packed attestation.

### 6. Policy Defaults

Registration is **denied by default** in agent profiles. The `AgentRpRule.register` policy must be explicitly set to `Allow` for each RP where the agent should be able to register credentials:

```toml
[[profiles.ci-agent.rules]]
rp_id = "gitea.example.com"
register = { authorization = "allow", user_presence = "none", user_verification = "none" }
authenticate = { authorization = "allow", user_presence = "none", user_verification = "none" }
```

This ensures that agents cannot register credentials on arbitrary relying parties without explicit policy configuration.

## Consequences

### Positive

- **Full autonomous lifecycle**: Agents can now register *and* authenticate, enabling complete headless workflows (setup → register → authenticate → rotate).
- **Same security model as authentication**: The daemon is the only entity that sees the private key. Origin, policy, grant, and audit gate every registration.
- **Works with TPM**: The `CredentialKeyProvider::generate()` abstraction supports both software and TPM key generation. TPM keys are generated and sealed in a single step; the private key never leaves the TPM.
- **Consistent architecture**: The registration path mirrors the authentication path (extension override → daemon endpoint → key provider), reducing cognitive load and maintenance burden.
- **No native modal**: The extension override prevents the browser's security-key modal, enabling fully headless registration.

### Negative

- **New attack surface**: The `/register` endpoint adds another HTTP endpoint that must be secured against origin spoofing, replay, and unauthorized registration.
- **Grant complexity**: The two-phase grant model (registration grant → authentication grant) adds complexity to the grant lifecycle and requires careful documentation.
- **Credential proliferation**: Agents can now create credentials without human oversight. If the policy is too permissive, agents may register credentials on unintended relying parties.
- **Attestation limitations**: Self-attestation ("none") may not be accepted by relying parties that require enterprise attestation. This is acceptable for the target use cases (Gitea/Forgejo) but may limit adoption.
- **Extension size**: The extension must now handle both `create()` and `get()` overrides, increasing its complexity and attack surface.

### Neutral

- **Registration is opt-in**: The default-deny policy means existing deployments are unaffected. Agents must be explicitly configured to allow registration.
- **No changes to human flows**: The human authentication and registration paths (via UHID) are unchanged. The extension only overrides when loaded into an agent-launched browser.

## Security Considerations

### Origin Validation
The `/register` endpoint performs the same structural origin verification as `/sign`: HTTPS only, exact host match, no port/path/query/fragment. This prevents origin spoofing attacks.

### Grant Scoping
Registration grants are scoped to specific RP IDs. An agent cannot register credentials on arbitrary relying parties; the policy must explicitly allow it.

### Exclude List
The daemon checks the `excludeCredentials` list against existing credentials for the RP. If a matching credential exists, the registration is rejected. This prevents duplicate credentials and complies with the WebAuthn specification.

### Audit Trail
Every registration is recorded in the audit log with the agent's identity, RP ID, credential ref, and timestamp. This provides a complete trail of all credentials created by agents.

### Key Generation
For TPM backends, the key is generated and sealed by the TPM in a single step. The private key never leaves the TPM, even during registration. This is the same security guarantee as authentication.

### Default Deny
Registration is denied by default. Agents must be explicitly configured with `register.authorization = "allow"` for each RP. This prevents accidental credential proliferation.

## Rollout

Implementation is sequenced to validate each layer before proceeding:

1. **Protocol types and grant system.** Add the registration grant types and lifecycle. Unit-test the grant resolution and policy evaluation. No daemon or extension changes yet.
2. **Daemon registration handler.** Implement the `/register` endpoint with full validation. Unit-test the handler with mock storage and key provider. Verify `authenticatorData` and `clientDataJSON` construction against the WebAuthn specification.
3. **Extension override.** Add the `credentials.create()` override to the extension. E2E-test against a controlled RP (test server) to verify the duck-typed credential is accepted.
4. **Real-RP E2E.** Repeat the E2E against the configured real RP (Gitea). Verify that the agent can register a credential and then authenticate with it.
5. **TPM E2E.** Repeat with a TPM backend to verify that key generation and sealing work correctly in the registration flow.

## Deferred Decisions

- **Automatic authentication grant after registration**: Whether the daemon should automatically create an authentication grant after successful registration, or require the agent to request a separate grant. The current design requires a separate grant request, but this can be revisited based on operator feedback.
- **Attestation formats beyond "none"**: Whether to support packed attestation or other attestation formats for relying parties that require enterprise attestation. The current design uses self-attestation ("none"), which is sufficient for the target use cases.
- **Batch registration**: Whether to support registering multiple credentials in a single request. The current design handles one registration at a time, but the architecture can be extended to support batch operations.
- **Registration policy expressions**: Whether to support more expressive registration policies (e.g., "allow registration only if the agent's process identity matches a specific digest"). The current design uses simple per-RP allow/deny policies.
